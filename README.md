# AI-помощник для подготовки товарных описаний

Прототип сервиса, который по данным контрольно-измерительного прибора собирает
черновик карточки товара для B2B-интернет-магазина: SEO-заголовок,
SEO-описание 800–1200 символов, таблицу характеристик, поисковые запросы и
commercial-блок для менеджера.

Главный принцип: **сервис не выдумывает характеристики**. Модель получает только
входные данные, а каждое значение в ответе дополнительно сверяется с ними в коде.
Если факта нет — в карточке появляется «данных нет», а поле попадает в отчёт о
недостающих данных.

Стек: Python 3.10+, FastAPI, Pydantic v2, httpx, Jinja2. Провайдер LLM
подключается через `.env`: OpenAI, Anthropic, Ollama или детерминированный
`mock` для запуска без ключа.

## Быстрый старт

Проект запускается **без API-ключа**: по умолчанию активен провайдер `mock`,
который собирает карточку детерминированно — этого достаточно, чтобы проверить
форму, API, формат результата, отчёт о недостающих полях и все пост-проверки.

### Windows (PowerShell)

```powershell
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
uvicorn app.main:app --reload
```

### Linux / macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload
```

Откройте <http://localhost:8000>. В форме можно нажать на название товара, чтобы
загрузить один из двух демо-примеров.

Проверка тестов (ключ и сеть не нужны):

```bash
pip install -r requirements-dev.txt
python -m pytest

## Подключение реальной LLM

Все настройки — в `.env` (файл в `.gitignore`, в репозитории лежит только
`.env.example`). API-ключ никогда не попадает в код.

### OpenAI

```ini
LLM_PROVIDER=openai
LLM_MODEL=gpt-4o-mini
LLM_API_KEY=sk-...
```

### Anthropic

```ini
LLM_PROVIDER=anthropic
LLM_MODEL=claude-3-5-haiku-latest
LLM_API_KEY=sk-ant-...
```

### Ollama (локально, без ключа)

```bash
ollama pull llama3.1
```

```ini
LLM_PROVIDER=ollama
LLM_MODEL=llama3.1
```

### Любой OpenAI-совместимый шлюз

```ini
LLM_PROVIDER=openai
LLM_BASE_URL=https://your-gateway.example/v1
LLM_MODEL=...
LLM_API_KEY=...
```

### Остальные параметры

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LLM_TIMEOUT` | `60` | Таймаут одного запроса, секунды |
| `LLM_MAX_RETRIES` | `2` | Повторы при таймауте, HTTP 429 и 5xx |
| `LLM_MAX_REPAIRS` | `1` | Дополнительные вызовы для исправления JSON/лимитов |
| `LLM_TEMPERATURE` | `0.2` | Температура генерации |

Если для OpenAI задан `OPENAI_API_KEY`, а для Anthropic — `ANTHROPIC_API_KEY`,
их можно не дублировать в `LLM_API_KEY`.

## Что получается на выходе

Ответ API — JSON с карточкой, отчётом о покрытии, метаданными и готовым Markdown:

```json
{
  "product": { "name": "...", "manufacturer": "..." },
  "card": {
    "seo_title": "до 70 символов",
    "seo_description": "800–1200 символов",
    "key_specs": [
      {
        "name": "Диапазон измерений",
        "value": "0–1,6 МПа",
        "source_field": "диапазон измерений"
      }
    ],
    "search_queries": ["3–5 запросов"],
    "commercial_block": "кому подходит и какие задачи решает",
    "notes": []
  },
  "missing_data": [
    {
      "field": "specs.материал корпуса",
      "reason": "значение не заполнено во входных данных"
    }
  ],
  "markdown": "# ...",
  "meta": {
    "provider": "openai",
    "model": "gpt-4o-mini",
    "attempts": 1,
    "duration_ms": 1840,
    "warnings": [],
    "generated_at": "2026-11-02T10:00:00+00:00"
  }
}
```

`source_field` показывает, из какой характеристики взято значение, — это удобно
для ручной проверки и для аудита.

## Как это работает

```
JSON / форма
    │
    ▼
Pydantic: нормализация и проверка входа
    │  нет фактов → 422 + список отсутствующих полей
    ▼
System prompt + входные данные + список пробелов
    │
    ▼
LLM-провайдер (OpenAI / Anthropic / Ollama / mock)
    │
    ▼
Разбор JSON: снятие ```-обёртки, ремонт запятых
    │  не разобралось → repair-запрос
    ▼
Проверки: длины, запросы, числа, привязка характеристик к входу
    │  есть замечания → один repair-запрос с точным списком проблем
    ▼
Детерминированная пост-обработка
    │  • недопустимые значения → «данных нет»
    │  • пропущенные характеристики → добавляются из входа
    │  • слишком длинный текст → аккуратная обрезка
    │  • короткий текст → предупреждение, без выдумывания
    ▼
Markdown + JSON + отчёт о недостающих данных
```

Ключевые слои:

- **`app/prompts.py`** — промпты: роль, жёсткие правила, JSON-схема,
  few-shot с «данных нет» и отдельный repair-промпт.
- **`app/verification.py`** — сверка фактов, лимиты и покрытие.
- **`app/pipeline.py`** — оркестрация, ограниченный цикл исправлений, метаданные.
- **`app/llm/`** — единый интерфейс провайдеров; HTTP-слой с таймаутами,
  повторами и понятными ошибками.

## Защита от выдуманных характеристик

Промпт — не единственная защита. Даже хорошая модель иногда добавляет «типичную»
характеристику, поэтому в сервисе есть независимая проверка в коде.

| Риск | Мера |
| --- | --- |
| Модель добавила характеристику, которой нет во входе | Каждое значение ищется в `specs` после нормализации (регистр, `ё`, тире, пробелы, запятая/точка в числах). Не нашлось — значение заменяется на «данных нет», менеджер видит предупреждение. |
| Модель изменила число (`1,5` → `1,6`, `100 мм` → `150 мм`) | Числа в значении должны совпадать с числами исходной характеристики. Иначе — «данных нет». |
| Модель придумала число в SEO-описании или commercial-блоке | Все числа из текста сверяются со всеми числами входа. При расхождении сначала отправляется repair-запрос, затем выводится предупреждение. |
| Модель пропустила характеристику | Недостающие характеристики добавляются из входных данных автоматически. |
| Модель написала «данных нет» там, где значение есть | Значение восстанавливается из входа с предупреждением. |
| Модель превысила лимиты 70/800–1200 | Лимиты проверяются в коде; заголовок и длинный текст обрезаются по границе слова/предложения. Слишком короткое описание не дополняется выдумками — выводится предупреждение. |
| Модель забыла перечислить пробелы | `missing_data` считается в коде по входным данным, а не генерируется моделью. |
| Невалидный JSON или обрезанный ответ | Снимается markdown-обёртка, ремонтируются висячие запятые, при неудаче — repair-запрос с текстом ошибки. |

Компромисс: проверка чисел намеренно консервативна и может дать ложное
срабатывание на безобидном числе. Это осознанный выбор — лучше показать
менеджеру предупреждение, чем молча опубликовать выдуманный факт.

## Промпты и принятые решения

**System prompt** задаёт роль редактора B2B-каталога и 10 жёстких правил:
источник фактов только входные данные, значения переносятся без изменений,
отсутствующее помечается «данных нет», заданы точные лимиты длины и формат
ответа. В промпт добавлен короткий few-shot: он показывает не только структуру,
но и правильное поведение с пустой характеристикой.

**Структурированный ответ.** Модель возвращает JSON по схеме: `seo_title`,
`seo_description`, `key_specs[{name, value, source_field}]`, `search_queries`,
`commercial_block`, `notes`. Для OpenAI используется JSON-режим, для Anthropic —
prefill ассистента символом `{`, для Ollama — `format: json`.

**Repair-цикл.** Если ответ не соответствует схеме или нарушает лимиты, сервис
делает один дополнительный вызов (настраивается через `LLM_MAX_REPAIRS`). В
запрос передаются конкретные проблемы, предыдущий ответ и повторное требование
не добавлять новых фактов. Цикл ограничен, чтобы не расти в цене и времени.

**Пост-проверка вместо доверия модели.** Все критичные гарантии — длины,
покрытие характеристик, отсутствие невыведенных чисел — проверяются
детерминированно. Поэтому качество не зависит только от того, насколько модель
послушна в конкретный день.

**Провайдеры за одним интерфейсом.** `LLMClient.generate()` скрывает различия
API. `mock` реализует тот же интерфейс и используется в тестах и демо-режиме.

**Ошибки как часть контракта.** Некорректный JSON — 422 с локализацией поля,
нехватка фактов — 422 со списком `missing_data`, сбой провайдера — 502 с
понятным сообщением, таймауты и 429/5xx повторяются с экспоненциальной паузой.

## Тесты

`103` теста, сеть и API-ключ не требуются:

```bash
python -m pytest
```

Что покрыто:

- нормализация входа, пустые и вложенные значения, отчёт о пробелах;
- нормализация чисел и тире, обрезка заголовка и описания;
- разбор JSON: обёртки, мусор вокруг, висячие запятые, ошибки схемы;
- анти-галлюцинации: подмена выдуманного значения, восстановление
  неверно помеченного, добавление пропущенного, числа в тексте;
- repair-цикл: исправление, исчерпание попыток, невалидный JSON;
- retry/timeout/401 на уровне HTTP-клиента без реальной сети;
- контракт API: 200/422/502, форма, Markdown, `/health`;
- конфигурация: провайдеры, ключи, некорректные числа в `.env`.

## Ограничения

- **Демо-данные.** В задании был только пример манометра DM 02; полный набор
  данных по двум товарам не предоставлялся. В `data/products.json` лежат пример
  из PDF и демонстрационный термометр, специально с неполными данными. Замена
  данных не требует изменений кода.
- **Mock — не LLM.** В режиме по умолчанию текст шаблонный. Он проверяет
  инфраструктуру и гарантии, но не качество креативности модели.
- **Нечисловые выдумки.** Сверка чисел и привязка характеристик ловят основные
  случаи, но утверждение без чисел («корпус из нержавеющей стали») нельзя
  доказать или опровергнуть автоматически, если его нет во входе. Здесь
  остаются промпт, `source_field` и обязательная проверка менеджером.
- **Консервативные предупреждения.** Проверка чисел может отметить безобидное
  число, которого нет во входных данных. Это сделано намеренно.
- **Один товар за запрос.** Массовая обработка — через повторные вызовы API;
  батч-режима, очередей и кэша нет.
- **Без БД, авторизации, CMS и деплоя** — по условиям задания это не требуется.
- **Длина считается как `len()` в Python.** Для русского текста этого
  достаточно; графемные кластеры и эмодзи отдельно не обрабатываются.
- **Стоимость.** Repair-вызов увеличивает расход токенов; по умолчанию разрешён
  один дополнительный вызов.

## Что можно улучшить дальше

1. **Набор оценочных кейсов (eval).** 20–30 товаров с эталонными фактами и
   автоматическая проверка полноты/галлюцинаций в CI — главный следующий шаг.
2. **Нативные structured outputs.** JSON Schema / tool calling у провайдеров
   снизят долю repair-вызовов.
3. **Батч и кэш.** Хэш входа → готовый черновик, параллельная обработка
   каталога, стриминг в UI.
4. **Редакционные правила.** Глоссарий, tone of voice, запрещённые формулировки,
   шаблоны под категории приборов.
5. **Наблюдаемость.** Трассировка промптов, стоимость, доля repair-вызовов,
   алерты на рост предупреждений.
6. **UI для контент-менеджера.** Инлайн-редактирование, подсветка
   «данных нет», сравнение версий, экспорт в CMS.
7. **Расширение нормализации.** Синонимы единиц, `мм рт. ст.`, допуски,
   диапазоны с разными разделителями.
